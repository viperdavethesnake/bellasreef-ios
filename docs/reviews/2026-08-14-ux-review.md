# UI/UX review — 2026-08-14

Reviewed live against the production hub (contracts 3.6.0) on an iPhone 17
simulator, app built from clean `main` at `47c4c7b` (v0.1.0). Judged against
the backend repo's `docs/ios-design-brief.md`: §2 palette law and §7 review
law. Severity judged against the bench (no tank, no livestock — a finding
that would be safety-relevant with stock is not one today).

Method: built and installed fresh, paired through the real code flow (one
fire-escape CLI window on the hub), driven screen-by-screen with synthetic
taps; every claim has a screenshot in `2026-08-14-ux/`. Nothing was adopted,
unadopted, revoked, or commanded. Shareable rendering of this review (same
content, same evidence):
https://claude.ai/code/artifact/3af65e68-ad8a-4bdb-9a75-6ee83fe9d520

**Verdict:** where built, the app holds its own review law. Data honesty
(§7.2) is the strongest part — History states bucket resolution and gap
status outright, the sparkline captions its true range and window, every
consequential control explains its consequence. Findings are mostly
absences, not dishonesty.

## Findings

Each carries a stable ID for a later plan. Severity: `fix` = brief
violation, `gap` = missing vs brief, `polish` = works but rough, `note` =
observation, owner may decline.

### UX-1 · fix · Light mode does not exist

- **Where:** `BellasReef/BellasReefApp.swift:39` — `.preferredColorScheme(.dark)`
  pinned at the root.
- **Law:** brief §2: "Light mode supported, secondary."
- **Evidence:** simulator appearance flipped to light renders the identical
  dark palette (screenshots were pixel-identical; `15-tank-live.jpg` is the
  shared appearance).
- **Resolution is a ruling, not just code:** either implement light mode or
  amend §2 to dark-only. The brief and the binary currently disagree, and
  the brief is review law.

### UX-2 · gap · No audit log view

- **Where:** System tab (`21-system-mid.jpg`, `20-system-scrolled.jpg` show
  the full tab: Hub, Paired devices, Hardware, Units, Sign out — no audit).
- **Law:** brief §3 tab 4 lists "audit log view"; PRD R16 names it.
- **API:** `GET /api/v1/audit?limit&category` exists and is unused by the app.
- **Resolution:** build it, or move it to the web UI's charter and amend the
  brief (the 2026-08-14 web-UI spec in the backend repo already includes an
  audit screen).

### UX-3 · gap · Equipment conflates "nothing adopted" with "adopted but silent"

- **Where:** Tank tab Equipment section (`15-tank-live.jpg`); System shows
  Front LED Bar and Back LED Bar adopted on pi-pwm ch 0/1
  (`21-system-mid.jpg`).
- **Law:** §7.1 state completeness.
- **Observed:** with two lights adopted, Equipment shows only "No channels
  reporting yet." Honest (no state frames arriving) but under-informative:
  the same copy would show with zero devices adopted.
- **Likely cause:** the section renders only from stream state frames, never
  from the device list.
- **Resolution:** list adopted actuators from `/devices` with an explicit
  per-row "no state yet," so the two conditions render differently.

### UX-4 · polish · Sparkline has no "collecting" state

- **Where:** Tank tab, fresh launch (`14-pair-attempt.jpg` vs
  `15-tank-live.jpg`).
- **Law:** §7.1.
- **Observed:** the sparkline region is blank until enough samples buffer,
  then line + caption appear. A "collecting…" placeholder would make the
  blank a designed state.
- Related note, no action required: the sparkline window is elastic
  ("last 75s" → "last 6m"), so equal slopes mean different rates at
  different ages. The caption keeps it honest.

### UX-5 · polish · Hero number looks tappable and is not

- **Where:** Tank tab. Tapping the temperature does nothing; only the
  probe-name row opens the detail sheet (`26-name-tap.jpg`).
- **Law:** §7.4 (target size is met; the issue is invisible affordance).
- **Resolution:** make the whole hero block (name + number + sparkline) one
  tap target for the detail sheet.
- **Outcome (2026-08-14, PR #2): withdrawn — tooling false negative.** The
  hero block was already one tap target (`Button` wrapping name + number +
  sparkline). A coordinate tap on the number's own frame opens the sheet;
  this review's synthetic CGEvent tap most likely landed on an active alert
  banner instead of the hero. No production change; `HeroTapTests` now pins
  the behaviour as a regression guard, with the diagnosis recorded at the
  top of the test file.

### UX-6 · note · Pair request created before the CLI window stays pending

- **Where:** pairing flow + hub CLI (backend repo), observed live.
- **Observed:** a code request created before `bellasreef pair` opened the
  window polled to expiry (`11-pairing.jpg`, still pending after the window
  opened); "Cancel and start over" then paired instantly (`14-pair-attempt.jpg`).
- **Semantics are coherent** (the window applies at request creation); the
  gap is copy. The CLI's "open the app and pair now" doesn't warn an
  operator whose phone already shows a code.
- **Resolution:** one sentence in the CLI output: "if a code is already
  showing, cancel and pair again." Backend change, not app.

  code screen with amber approval state, countdown, restart (`11-pairing.jpg`).

  pair (`14-pair-attempt.jpg`); Lighting is an honest "Not built yet"

  explicit "No gaps at this resolution (9 min / 45s)" per range
  (`17-history.jpg`, `18-history-1h.jpg`).
- §2 palette: teal sole accent + healthy; amber = attention; red only on
  destructive controls (Revoke/Unadopt/Sign out — the v1.2 control-red
  carve-out). No decorative red in status or data anywhere observed.
- §7.6 glass: tab bar and sheets only; content solid; iOS 26 minimizing tab
  bar behaves over scroll.
- §7.5 Dynamic Type: accessibility-extra-large reflows without truncation on
  Tank (`28-dynamic-type.jpg`).

  records Celsius; this only changes what you see"); sign-out consequences
  stated (`20-system-scrolled.jpg`).
